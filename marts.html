Dimension

dim_customer from the PIT

The PIT has one row per customer per day. Most days nothing changes, so consecutive rows point to the same satellite rows. Collapsing those runs gives one row per version of the customer, with a validity range: a type-2 dimension.

Built with joins only


      
    
        
  • There is no business logic here, only equi-joins from the PIT to the satellites and a group-by. Rules such as "what counts as a Gold customer" belong in the Business Vault, before this step.
    • 
        
  • The ghost record gives Ben a row for Jan 02 with an empty city, instead of dropping him until his address arrives.
    • 
        
  • These are the same rows the dbt snapshot produced on the snapshots page. The difference is that this table can be dropped and rebuilt, because the satellites hold the history.
    • 
        
  • For a dimension without history (type 1), read only the latest PIT snapshot.

Fact

  
fact_order from the bridge

  
The bridge already knows which customer, order and product belong together. The fact table adds the measures from the order satellite and, for each order, the key of the customer version that was valid on the order date.

  
  

    

    

      
Built from the bridge

      
    
        
  • customer_key points to one specific version in the dimension, not to the customer in general. That is what makes "as it was at the time" reporting possible.
    • 
        
  • Without the bridge, this query walks hub, link, hub, link, hub and repeats that walk in every fact.
    • 
        
  • Measures can be stored in the bridge itself when the same ones are needed by several facts.

Report

  
Revenue by segment, two ways

  
Anna ordered as a Bronze customer, was upgraded, and ordered again. Which segment gets her revenue? Both answers are valid, and a type-2 dimension can give either one.

  

    

      

      

    

    

      

      

    

  

  
    
    
  • As it was joins the fact to the exact version stored on the fact row. Use it for questions about behaviour at the time: "how much do Bronze customers spend?"
    • 
    
  • As it is today joins to the customer's current version. Use it for questions about today's groups: "how much have our current Gold customers spent in total?"
    • 
    
  • Move the date back and watch the right-hand table change while the left-hand one only grows. Past results in the left table never change.

Rules of thumb

  
What a mart is and is not

  
    
    
  • Disposable. A mart holds no history of its own. Everything in it can be rebuilt from the vault, so changing a mart never puts data at risk.
    • 
    
  • Start virtual. Build dimensions and facts as views first. Materialise them as tables only when queries become too slow.
    • 
    
  • No business rules. Calculations and classifications live in the Business Vault, where they are versioned and shared. A mart only reshapes.
    • 
    
  • Many marts, one vault. Finance and marketing can each have their own star schema with different names and grain, built on the same hubs, links and satellites.
    • 
    
  • Not only star schemas. The same vault can feed flat tables for data science or an API. The star schema is just the most common shape.
