Data pipeline performance tuning

A pipeline is only as fast as its slowest stage. Most tuning wins come from finding that stage and fixing one of a few common causes: too much data read, too much data moved between workers, uneven work, or slow writes.

Step 1

Measure before you tune

Without numbers you'll tune the wrong thing. Record these for every stage on every run, and keep the history so you can see slow drift.

Per-stage metrics
metrictells you
wall_clock_swhere the minutes go
rows_in / rows_outjoin fan-out, filters that don't filter
bytes_readwhether pruning works
shuffle_bytesdata moved between workers
spill_bytesmemory pressure
task_max / task_medianskew
cpu_pctcompute bound, I/O bound or waiting

Where to look

  • Spark: the stages tab in the Spark UI, and EXPLAIN FORMATTED for the plan.
  • SQL warehouses: the query profile or EXPLAIN ANALYZE: bytes scanned, partitions pruned, spill.
  • Orchestrators (Airflow, Dagster, ADF): task durations over time.

Step 2 · Reading

Read less data

The cheapest row is the one you never read. Columnar formats, partitions and early filters all cut how much has to come off disk or over the network.

  • Columnar formats. Parquet, ORC, Delta and Iceberg let readers fetch only the needed columns and skip blocks using min/max statistics.
  • Partitioning. Partition on a low-cardinality column you always filter by, usually a date. Partitioning by user ID or timestamp creates thousands of tiny files.
  • Clustering / Z-ordering. Sort data within files on high-cardinality filter columns, so more blocks can be skipped.
  • Pushdown. Filter rows and select columns as early as possible, ideally in the source query.
  • File sizes of roughly 128 MB to 1 GB, compressed with Snappy or ZSTD.

Blocks pruning

-- the function hides the partition column
select *
from events
where date(event_ts) = '2026-11-10'

Prunes

-- filter the partition column directly,
-- select only what you need
select user_id, amount
from events
where event_date = '2026-11-10'

Step 3 · Reading

Process only what changed

A full reload gets slower every day, because history keeps growing. An incremental load costs about the same every day, because it grows with the daily volume instead.

How it worksWatch out for
WatermarkRead rows where updated_at is later than the last high-water markLate-arriving rows, clock drift, a column the source doesn't always maintain
CDCRead inserts, updates and deletes from the source's change logSetup effort, ordering, schema changes
Partition overwriteRebuild only the partitions that changedYou must know which partitions changed
HashdiffCompare a hash of the row with the stored one and load only the differencesStill reads the full source, but writes much less
 
merge into dw.orders t
using (
  select * from staging.orders
  where updated_at > :last_watermark
) s
on t.order_id = s.order_id
when matched then update set *
when not matched then insert *
  • A merge on a stable key is idempotent: running it twice gives the same result, so retries are safe.
  • The hashdiff pattern is the same one the satellite loader uses on the hashing and loading page.
  • Late-arriving data needs care with any watermark. See the time page.

Step 4 · Compute

Move less data between workers

Joins, group by, distinct and window functions redistribute rows across the cluster. These shuffles cost network, disk and memory, and they are usually the most expensive part of a distributed job.

Use whenCost
Broadcast joinOne side is small, up to a few hundred MBSmall side copied to every worker; big side stays put
Sort-merge joinBoth sides are largeBoth sides shuffled and sorted
Shuffle hash joinOne side fits in memory per partitionBoth sides shuffled, no sort
Bucketed joinThe same tables are joined on the same key again and againShuffle paid once, at write time
 
# PySpark: broadcast a small dimension
from pyspark.sql.functions import broadcast
facts.join(broadcast(dim_country), "country_id")

# let adaptive execution resize partitions
spark.conf.set("spark.sql.adaptive.enabled", "true")

Do

  • Filter and aggregate before joining
  • Drop wide columns before the shuffle
  • Reuse one partitioning across consecutive steps

Avoid

  • Joining before filtering
  • Several distincts where one group by would do
  • Accidental cross joins from a missing join key

Step 5 · Compute

Spread the work evenly

A parallel stage finishes when its slowest task finishes. If one key holds a large share of the rows, one task gets all of them while the rest of the cluster waits.

Spotting skew

  • The slowest task takes many times longer than the median.
  • One partition is far larger in shuffle read size.
  • A few keys hold most rows, often null, 'unknown' or a test account.

Fixing it

  • Handle null keys separately if they can't match anyway.
  • Broadcast the other side if it is small enough.
  • Salt the hot key: add a random suffix on the big side and duplicate the matching rows on the small side.
  • Let Spark AQE split skewed partitions (spark.sql.adaptive.skewJoin.enabled).

Sizing parallelism

  • Aim for partitions of about 100–200 MB after a shuffle.
  • Run 2–3 tasks per CPU core, so fast tasks fill the gaps.
  • Read sources in parallel too. A single JDBC connection is a common hidden bottleneck.
-- find the hot keys
select customer_id, count(*) as n
from orders
group by customer_id
order by n desc
limit 20

Step 6 · Writing

Load in bulk

Row-by-row writes through a database driver are often the slowest part of an otherwise fast pipeline. Stage files and load them in one statement instead.

Typical throughput · orders of magnitude
approachrows / s
row-by-row insert10² – 10³
batched insert10⁴
copy from staged files10⁵ – 10⁶+

Real numbers depend on row width, the warehouse and the network.

  • Bulk loads. Stage files in object storage and use copy or a set-based merge.
  • Fewer, larger files. Repartition before writing. Many tiny files slow down every later read.
  • Compaction. Streaming and micro-batches create small files; compact them on a schedule (optimize in Delta, rewrite_data_files in Iceberg).
  • Indexes. On row stores, index maintenance slows big loads. Some teams drop and rebuild indexes around them.
  • Commits. Commit in batches, not per row.

Step 7 · Compute

Memory, spill and caching

When a sort, join or aggregation doesn't fit in memory, it spills to disk and slows down sharply. Check for skew before adding memory: one oversized partition spills no matter how big the cluster is.

Do

  • Use more, smaller partitions, and carry fewer columns
  • Cache a cleaned table that several outputs reuse, and unpersist it afterwards
  • Prefer built-in SQL functions
  • Check the spill columns in the job metrics

Avoid

  • Caching everything by default
  • collect() or toPandas() on large data, which pulls it all onto one machine
  • Python UDFs for simple string or date logic: they serialise every row and block optimisations
  • Raising memory before checking for skew

Step 8

Orchestration and cost

The total run time is set by the longest chain of dependent tasks, not by the sum of all tasks.

extract_crm6 min
→
transform_orders31 min · critical path
→
load_marts9 min
  • Run independent tasks in parallel. A DAG that runs everything in sequence leaves most of the cluster idle.
  • Shorten the critical path first. Speeding up a task off that path doesn't change the end time.
  • Right-size compute per task: a small cluster for light tasks, a large one for the heavy transform.
  • Autoscaling and spot instances cut cost for fault-tolerant batch work.
  • Schedule around contention. Shared warehouses slow down at peak hours.
  • Track cost per run next to run time. A run that is twice as fast and four times as expensive isn't always a win.
  • Plot run time per day. A slow, steady climb usually means full reloads or piling-up small files.
