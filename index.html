dbt snapshots, PIT tables and bridges

Three structures that all carry a date column and all get called "snapshots" in conversation. They do different jobs. Below, the same seven days of customer and order data run through each of them.

The shared data

Two customers, three orders, seven days

The source system overwrites in place. A customer has a segment (maintained in the CRM) and a city (maintained in the address service). Anna (C-1) is upgraded twice and moves once. Ben (C-2) signs up on Jan 02, but his address only arrives a day later. Three orders link customers to products.

dbt · history capture

dbt snapshot

A snapshot turns a mutable source table into a type-2 history table. Each dbt snapshot run compares the source with the latest stored version. If a row changed, it closes the old version and inserts a new one. One row per version.

Result

      
    
        
  • It stores the attributes themselves. dbt adds dbt_valid_from, dbt_valid_to, dbt_scd_id and dbt_updated_at.

  • It only sees what exists when it runs. Had Anna gone Bronze → Silver → Gold between two runs, Silver would never be recorded.
    • 
        
  • This table is the history. It cannot be rebuilt from the source, so it is never full-refreshed.
    • 
        
  • Orders would need a second snapshot, orders_snapshot. Relationships are just columns in whichever row carries them.

Data Vault · query helper for attributes

  
PIT table (point in time)

  
In a Data Vault the history already exists: segment lives in one satellite, city in another, each versioned by load date. Getting "the customer as of day X" means finding the right row in every satellite. A PIT table precomputes that lookup. One row per customer per snapshot date, holding only pointers.

  
  

    

      

        

        

      

      

    

    

      
As-of query

      
Result

      
    
        
  • Same answer as the dbt snapshot, but the PIT holds no attributes. It turns range lookups against every satellite into plain equi-joins.
    • 
        
  • Rows grow with keys × snapshot dates, not with changes. Old dates are usually thinned out, for example daily for a month, then month-ends only.
    • 
        
  • Ben has no address on Jan 02. The PIT points to a ghost record (load date 1900-01-01) so inner joins never drop him.
    • 
        
  • It is disposable. Drop it and rebuild it from hub and satellites at any time.

Data Vault · query helper for relationships

  
Bridge table

  
A PIT goes down from one hub into its satellites. A bridge goes across: it walks from hub to link to hub and stores the resulting key combinations. One row per relationship path per snapshot date.

  

    hub_customer—link_customer_order—hub_order—link_order_product—hub_product⇒bridge_customer_order_product
  

  
  

    

    

      
As-of query

      
Result

      
    
        
  • It answers a different question from the other two: not "what did the customer look like?" but "what was connected to what?"
    • 
        
  • It stores keys only, sometimes with precomputed measures. Attributes come from each hub's PIT, joined on the same snapshot date.
    • 
        
  • Without it, the query above is a four-join walk through two links, repeated in every mart.
    • 
        
  • Also disposable. Watch the fan-out: every extra link multiplies paths, and every snapshot date multiplies them again.

How they fit together

  
They are stages, not alternatives

  

    
sourceOverwrites rows in place
→
    
dbt snapshotNeeded only if the source delivers no change history
→
    
raw vaultHubs, links, satellites keep all history
→
    
PITPointers into satellites

    
bridgePaths across links
→
    
martsDimensions from PITs, facts from bridges

  

  
    
    
  • No Data Vault: a dbt snapshot is usually all you need. It already is a type-2 table, and a dimension can be built straight on top of it.
    • 
    
  • Data Vault: satellites do the job of the snapshot, so PITs and bridges are added afterwards purely for query speed and simpler mart SQL. dbt packages such as AutomateDV generate both from macros.
    • 
    
  • Both: a snapshot sits in front of the vault when a source has no change feed and is only loaded occasionally. The vault then loads from the snapshot instead of the raw table.
