Hash keys and loading patterns

How a row gets from a staging table into the vault. Two hashes do most of the work: one says which thing a row is about, the other says whether anything changed. With those in place, every load is the same simple insert.

Identity

Hash keys

A hash key is computed from the business key and nothing else. Any loader can work it out on its own, without looking up a sequence number in another table. That only works if every source writes the same key the same way, so the key is cleaned before it is hashed.

In SQL


    
    
      
  • The hash is the join key everywhere: hubs, links, satellites, PITs and bridges all carry it.
    • 
      
  • A link's hash key is built from the business keys of all its hubs, not from their hash keys.
    • 
      
  • A missing key part is replaced by a fixed placeholder, so the hash is always defined. Rows with no business key at all go to a reserved "unknown" hub row.
    • 
      
  • MD5 is the traditional choice. SHA-1 or SHA-256 are used where collision risk or security policy matters. Store the result as binary, not text, where the database allows it.
    • 
      
  • Fix the rules once (trim, case, delimiter, placeholder, algorithm) and never change them. A changed rule means every key in the vault changes.
    • 
    

  






  
Change detection

  
Hashdiff

  
A satellite should get a new row only when something changed. Comparing every column against the previous row is slow and awkward to write, so all descriptive columns are hashed into one value, the hashdiff. Same hashdiff as the latest row: skip. Different: insert.

  • Column order is part of the definition. Hash the columns in a fixed order, with a delimiter, and with nulls replaced by a placeholder.
    • 
    
  • Unlike business keys, attribute values are usually not upper-cased. A change from graz to Graz is a real change in the source.
    • 
    
  • Adding a column to a satellite changes every hashdiff. Either accept one extra row per key on the next load, or put the new column in a new satellite.
    • 
    
  • The hashdiff is stored in the satellite row, so the comparison is against one column of the latest row.

The three load patterns

  

    

    

    

  

  
    
    
  • Hub: insert the business keys that are not there yet.
    • 
    
  • Link: insert the key combinations that are not there yet.
    • 
    
  • Satellite: insert a row when the key is new or its hashdiff differs from the latest row.
    • 
    
  • Safe to re-run. Loading the same batch twice inserts nothing the second time, because every pattern checks what is already there.
    • 
    
  • No load order. Hash keys come from the staged data, not from a lookup in the hub. Hubs, links and satellites can all load at the same time.
    • 
    
  • Deletes are invisible. A row missing from the extract inserts nothing. Tracking deletions needs a status tracking satellite, shown on the model types page.
