Modelling decisions

  • Rental is a hub, not just a link. It has its own identifier, payments refer to it, and it changes after creation (the return date is filled in later). The link LNK_RENTAL records who rented which copy from which staff member; SAT_RENTAL holds the dates.
  • Payment is a non-historized link. A payment is an event that is never edited, so the amount and date sit directly in the link and no hub or satellite is needed.
  • Every foreign key became a link. A hub never stores another hub's key. Where the foreign key can change (a customer's store or address, a store's manager), the link gets an effectivity satellite, because link rows are never deleted or updated.
  • Language, city and country are reference tables. They are code lists that only describe other things. Category is a hub instead, because films relate to it many-to-many and it is something the business analyses by.
  • Address is a hub. Customers, staff and stores all point to the same address table, so it is one shared concept with three links, not attributes copied into three satellites.
  • Staff attributes are split by sensitivity. Username and password hash go into their own satellite so access can be restricted separately.
  • The business keys are weak. The source only has surrogate IDs (customer_id, film_id), so they are used as business keys here. In a real project, look for the key people actually use, and add a business key collision code if a second source reuses the same numbers.
  • Data Vault 2.1 columns. Besides the hash key, LOAD_DTS and RECORD_SOURCE, 2.1 models commonly carry an applied timestamp (when the data was valid in the source, as opposed to when it was loaded) and, in multi-tenant setups, a tenant ID. They are left out of the column lists to keep them short.
