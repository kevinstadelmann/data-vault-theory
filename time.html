Time in a Data Vault

"What was the customer's city on Jan 06?" has two honest answers: what was true, and what the warehouse knew at the time. They differ whenever data arrives late. A vault keeps both by storing two dates on every row.

Applied date: when it became true in the source Load date: when the vault received it Snapshot date: the day a query asks about

Two timelines

Load date and applied date

Same customers as on the snapshots page, with one difference: the address service is slow. Anna moved to Wien on Jan 05, but the change only reached the warehouse on Jan 07. For two days the vault held an answer that was already out of date.

Result

    

  

  
    
    
  • Load date is set by the warehouse when the batch arrives. The source cannot influence it, so it never goes backwards and can always be trusted.
    • 
    
  • Applied date comes from the source: a change timestamp, an extract date or a file date. It can be late, back-dated or simply wrong.
    • 
    
  • Filtering on load date reproduces a report exactly as it looked on the day it was run. That is what auditors ask for.
    • 
    
  • Filtering on applied date gives the best current knowledge of the past. That is what analysts usually want.
    • 
    
  • A PIT table can be built on either timeline. Decide which question it answers and name it accordingly.

Validity

  
End dates are computed, not stored

  
A satellite row says when it started. It does not say when it ended, because that is only known once the next row arrives, and writing it back would mean updating an old row. The end date is worked out at query time from the next row's load date.

  

    

    

      
View over the satellite

  • Updating old rows breaks the insert-only rule and is expensive on columnar and data-lake storage, where an update rewrites whole files.

  • If the window function is too slow at query time, the result is materialised in a PIT table, which can be rebuilt at any time.

  • Older Data Vault 1.0 models stored a load_end_date column and updated it. Current practice is to leave it out.

Late arrivals

  
Data that arrives out of order

  
Sometimes a whole batch is late. Suppose the Jan 03 file that upgraded Anna to Silver got stuck, and is only loaded on Jan 08, after the Jan 07 file that made her Gold.

  

    

    

  

  
    
    
  • Read in load order, Anna appears to be downgraded from Gold to Silver. Read in applied order, the history is correct.
    • 
    
  • The standard satellite loader compares a staged row with the latest row by load date. For a late batch it must compare with the row just before it in applied-date order instead.
    • 
    
  • The dangerous case is a late row that looks identical to the current one. Bronze, then Silver, then back to Bronze: if the Silver file is late, a naive loader sees Bronze twice in a row, skips the second, and the return to Bronze is lost once Silver is inserted.
    • 
    
  • After a late batch, PIT and bridge tables for the affected dates are rebuilt. That is safe because they hold no history of their own.
    • 
    
  • If a source can never deliver late, none of this is needed. Find out before building it.
    •
